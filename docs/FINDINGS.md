# What a systematic audit of a "finished" identity service found

A working note on defect *patterns* — the kind that survive review, ship to
production, and stay invisible because everything reports green.

Context: notme is a small identity authority (Cloudflare Workers, X.509 +
WebAuthn + OIDC). It had tests, threat-model rows linked to those tests, ADRs,
and a CI gate that verified documentation claims. It looked done.

---

## The number that matters, and the one that doesn't

Open work items went from ~70 to ~87 during the audit.

**That is the mechanism working.** The goal is *zero **unknown** release
blockers*. An audit that surfaces 17 defects converts 17 unknowns into 17
knowns — the count rises precisely because the thing is succeeding. A count
that stayed flat would mean nobody looked.

The metric that matters is severity, and it moved the other way:

| | At audit start | Now |
|---|---|---|
| **P0** | 5 | 5 addressed — 4 fixed and deployed, 1 awaiting external confirmation |
| Tests | — | 662 passing (538 unit + 124 real-Durable-Object) |
| Commits | — | 109 (29 fixes, 7 features, 20 doc corrections, 1 CI gate) |

---

## Three patterns, each found more than once

### 1. An artifact asserting a property of its own provenance that nothing verified

The artifact makes a claim *about itself*, and nothing anywhere checks it.

- A certificate carried `authMethod` describing how the user authenticated —
  derived from a field the mint path never validated.
- A CI workflow declared outputs that were **structurally always empty**; three
  PRs consumed them.
- A committed build artifact asserted it came from sources it hadn't been built
  from in weeks.
- A threat model credited the wrong defence: *"CryptoKey is not Structured
  Cloneable — cannot cross RPC boundary."* It is Serializable, `structuredClone`
  succeeds, and the codebase's own RPC method takes two `CryptoKey` parameters.
  **The key is genuinely safe** — via non-extractability — but the stated reason
  is false, so nobody could have caught it being violated.
- An ADR asserted an RFC guarantee **the RFC does not give**: that URI
  `nameConstraints` restrict a URI's *path*. RFC 5280 §4.2.1.10 binds the
  **host**. Anyone building on that section would have found nothing enforced.

### 2. A green test proving a real property of a path production never takes

The test is correct. The property is real. Production doesn't go that way.

- A bootstrap test exercised the one function the passkey flow never calls.
- A scope-attenuation rule — *"MUST check, not optional"* per its ADR — existed
  **only as a helper defined inside the test file**. Six passing tests covered a
  one-line reimplementation; production had no check at all.
- Canonical-encoding fixtures were generated by the encoder they validated. Any
  self-consistent encoder passes, including a wrong one — and one was wrong, for
  months.
- A test file containing `expect(true).toBe(true); // Placeholder` imported *no
  production code*, while the threat model pointed at it as a defence.

### 3. A correction that reached the ADR but not the surface that carries it

The newest one, and the nastiest: **corrected text reads as *more* trustworthy,
so nobody re-checks it.** The word CORRECTED tells a reader to stop looking.

- An ADR retracted an integration instruction as *"would have broken the first
  integrator to follow it."* The 404 error body still hands integrators that
  exact instruction.
- An ADR still teaches the encoding that caused a production incident — and it
  is the document another repository implements against.

## Two that don't fit the patterns, and are worth their own mention

**The green signal that measured the wrong thing.** A canary reported a healthy
10/90 traffic split while **85 of 85 samples hit the old version**. Two later
attempts to build a version discriminator also failed — one because the chosen
signal (a JWKS key id) was *stored database state*, identical across builds, so
it could not distinguish versions even in principle.

The root cause, once a build-derived identifier existed to measure it: **"100%"
is not immediate.** After the API reported promotion complete, live traffic
alternated between old and new for about a minute. The control plane reports
*intent*; the data plane arrives later. Verification retried for ~10 seconds
against a ~60-second window — so a deploy's green light was partly luck.

**The audit that reads the wrong file.** A dependency override pinning a package
away from three advisories sat **inert for weeks** while `pnpm audit` reported
clean. Audit reads the *lockfile*; the vulnerable copy was in a **committed
build artifact** that nothing rebuilt. Two different files, one of them the
thing that actually executes.

## The inverse case, which is rarer and worth naming

Exactly one finding ran the other way: **the document was right and the code
regressed.**

An ADR specified a minimum entropy floor for the secret that encrypts the CA
master key — including the exact fatal error message. The implementation plan
specified the *test*. Neither shipped. A four-character secret booted the
service reporting encrypted storage: the appearance of sealing, none of the
strength.

Everywhere else the code was correct and the documentation overclaimed. This is
the reminder that the failure is not directional — it is that **nothing was
comparing the two.**

## What actually helped

Not more tests. Tests were the *source* of several false signals.

1. **Ask what would have to be true, then check it against the artifact that
   ships.** Not the source, not the config — the thing that executes.
2. **Fixtures must be foreign.** A fixture built by the code under test is a
   fixed point, not a conformance check.
3. **Make gaps executable.** Tests asserting a gap *still exists* (`it.fails`)
   turn red the moment someone closes it — which is the signal to celebrate,
   not to fix the test.
4. **Discriminators must derive from the build, never from data the build
   reads.** This is why the key-id attempt could not have worked.
5. **When a correction lands, find every surface carrying the old claim.**
   The ADR is the easy one. The error string is the one an integrator hits.

## What is still open, stated plainly

Nothing here revokes a credential before its TTL expires. The revocation module
is complete, tested, and **has no call sites**; separately, capability grants
are read from a session cookie rather than re-checked. Two documents describe
revocation as working. That is the largest remaining gap, it is now known and
enumerated, and it is gated on a design decision rather than effort.

The documentation-honesty pass is the one unbounded item. It found five
artifacts asserting unverified properties in a cycle where nobody was looking
for them systematically.
