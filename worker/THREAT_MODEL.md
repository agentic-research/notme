### 1c. invites (POST /invites, POST /join)

An invite is a bearer way in: whoever holds the token gets the scopes it names, `authorityManage` included.

| threat | attack | defense | test |
| --- | --- | --- | --- |
| invite outlives a reset | mint an `authorityManage` invite, then rely on it after `resetPasskeyData` wiped every passkey — a way in `#hasAuthenticator` does not count | **FIXED (notme-2131e8)** — `resetPasskeyData` deletes every unredeemed invite in the same call that wipes the credentials and rotates the session secret. Redeemed rows stay as the audit trail. | `invite.reset.revokes` |
| unbounded invite lifetime | `POST /invites` with `ttl` of years — the TTL was caller-supplied and went straight into `expires_at` | **FIXED (notme-2131e8)** — `createInvite` clamps to `INVITE_MAX_TTL_SECONDS` (7 days, the ceiling the invite form already stated) and refuses a non-finite TTL; the route answers 400 for a non-numeric one. | `invite.ttl.ceiling`, `invite.ttl.finite` |
| invite burned by a failed ceremony | start a passkey registration with someone's invite and cancel it — `register/options` redeemed the invite before the ceremony happened, so the legitimate invitee was locked out | **FIXED (notme-3dfe15)** — options (and `POST /join` without a proof) only RESERVE the invite for one WebAuthn user id; it is consumed when that user's credential verifies. | `invite.join.failed-ceremony-keeps-invite` |
| invite scopes silently dropped | redeem an `authorityManage` invite with a passkey — verify enrolled the new principal with `bridgeCert` regardless | **FIXED (notme-3dfe15)** — verify consumes the reservation and creates the principal with the INVITE's scopes. The consume, the principal, its grants, the `passkey_users` row and the credential are one `transactionSync` (review L1 — the first version committed the consume before the credential inserts, so a throwing insert left the invite spent and a credential-less principal holding its scopes); a throwing store rolls all of it back. | `invite.join.keeps-scopes`, `invite.join.store-atomic` |
| registration past the gate | complete a ceremony whose reservation was superseded or expired — the gate lived only at options, and `ensurePasskeyPrincipal` granted `bridgeCert` to any verified credential | **FIXED (notme-3dfe15)** — `verifyRegistration` takes an `admit` hook that runs after the attestation verifies and before any insert; outside first-user, claim, or a live reservation it refuses and stores nothing. | `invite.join.single-use` |
| session with no authenticator | `POST /join {token}` — redeemed the invite and issued a session for a principal with no passkey and no linked identity, invisible to `#hasAuthenticator` | **FIXED (notme-3dfe15)** — without a proof `/join` returns registration options and no session. | `invite.join.no-authenticator` |
| bad OIDC proof still joins | `POST /join` with a garbage OIDC proof — verification failure was swallowed, the invite burned and a session issued | **FIXED (notme-3dfe15)** — the proof is verified before anything is written; failure is 403 (`ERROR_STATUS.OIDC_PROOF_REJECTED`). An identity already linked to a principal is refused (409) instead of being moved by `INSERT OR REPLACE`. The rejection body is the constant `invalid oidc proof` (verifier detail is logged), and the invite is checked BEFORE the link, so a garbage invite answers 403 whether or not the identity has joined — no link oracle (review L4). | `invite.join.bad-oidc`, `invite.join.oidc-success`, `invite.join.oidc-already-linked`, `invite.join.oidc-no-link-oracle` |
| reservation hijack | learn an invitee's in-flight `userId`, send a wrong attestation to learn the expected challenge from the 500 body (`@simplewebauthn` names it), then finish the ceremony with your own authenticator and take the invite's scopes | **FIXED (review M1)** — the passkey 500 body is a constant (the message is logged server-side); a failed verify burns its challenge; and a reservation is bound to the reserving browser by an HttpOnly, Secure, SameSite=Strict `notme_invite_reservation` cookie whose secret is stored only as a SHA-256 on the reservation and is required at consume. Without it the reservation can be neither used nor cancelled. Residual: anyone who knows the userId can still send a junk attestation, which burns the challenge and forces the invitee to start the ceremony again; the invite itself is not spent. | `invite.join.failed-ceremony-keeps-invite`, `invite.join.failed-verify-burns-challenge`, `invite.join.reservation-cookie` |
| "first user" by passkey count | on an authority whose administrator signs in by OIDC (no passkey user), every invitee hit the bootstrap gate; and verify's admit trusted the same `passkey_users`-is-empty count, so any registration reaching verify there was made the admin | **FIXED (review L2)** — first-user standing is the DO's `registrationIsFirstUser`: no passkey user AND no live `authorityManage` holder with a linked identity (a bare-principal or reset-stranded admin still goes through bootstrap, which is its recovery path). Options consumes the code and MARKS the userId (`beginFirstUserRegistration`); admit makes a registrant the admin only on that mark. | `invite.first-user.oidc-admin`, `invite.first-user.admit-gate` |
| revoked inviter's invites | an admin mints a 7-day `authorityManage` invite, loses `authorityManage`, then redeems the invite to get it back — `canGrant` ran only at mint | **FIXED (review M2)** — `liveInvite`, the predicate every reserve, consume and OIDC join goes through, re-checks `canGrant` against the inviter's CURRENT grants for every invite scope and refuses the whole invite if any fails. | `invite.consume.inviter-live` |
| invite token in a logged URL | read the bearer token out of Workers invocation logs — `POST /invites` returned `/join?t=<token>`, and every request that opened the link logged its URL | **FIXED (notme-3dfe15)** — the link is `/join#t=<token>`; a fragment is never sent to the server. `GET /join` no longer requires a query token; `_login.html` reads `location.hash`, POSTs the token in a body, and scrubs it from history. `_invite.html` shows the server's link verbatim (it used to build its own `?code=` link, which `/join` never read). Already-logged tokens (review M3): neither the server nor the page reads a legacy `?t=` any more, and `liveInvite` treats any invite whose lifetime exceeds the 7-day ceiling as dead, so a pre-fix years-long invite does not survive the deploy. A logged token under 7 days old can still be pasted until it expires. | `invite.link.fragment`, `invite-link-pages.test.ts`, `invite.ttl.legacy-dead` |
| replayed OIDC proof on /join | present a captured id_token (aud `notme.bot`, unexpired) with an invite, linking that identity to a principal the attacker holds a session for | **INTERIM FIXED (notme-3dfe15 part 1, option A); OPEN for the nonce (option B, notme-e3dede).** The residual was squatting: a replayed token for a never-linked identity X bound X to a principal the attacker created and held a 24h session for; X's own later invite join got 409, X's later `/auth/oidc/login` landed in that principal, and audit attributed the attacker's actions to X. The tokens `/join` accepts are the same aud-`notme.bot` tokens `/cert/gha`, `/cert` and `/token` spend, so "captured" included "already spent at another route" — and on the base code a token spent at `/cert/gha` still joined. Now an OIDC proof at `/join` is single-use by `jti`: (1) no `jti` is 400, fail closed, as `/cert/gha`; (2) a `jti` already spent in the shared `jti:<jti>` KV keyspace (`/cert/gha`, `/cert`, `/token`, `/bootstrap/claim`) is refused (401 `token already used`); (3) the authority DO consumes `oidc:<issuer>#<jti>` in `dpop_jtis` — the ONE key `/auth/oidc/login` also spends (re-review N1: per-route keys left KV as the only guard between the two legs, so a token just spent at `/join` could log in before KV propagated; `login.oidc-jti.cross-leg`) — the same table and the same `INSERT OR IGNORE` + `changes()` consume `mintDPoPTokenOnce` uses, now the shared `#consumeJti` — inside the `transactionSync` that redeems the invite and links the identity, so a concurrent replay cannot race the first use and the refusal does not depend on the link row surviving; (4) a successful join writes `jti:<jti>`, so the token cannot then buy a cert elsewhere. TTL is `exp + 300s` (DO, see F2 below) and `max(JTI_MIN_TTL_SECONDS, exp - now)` (KV, as `/cert/gha`). A REFUSED join spends nothing: the invite and the link are checked before the consume, and the consume is rolled back with the transaction — `/join`'s contract is that a refusal spends nothing (the invite stays live on 409), matching `/cert` and `/token`, which spend the jti only after their proofs verify. An attacker probing with a captured token still needs a live invite, and with a garbage invite the answer is 403 whatever the token's history (the spent-elsewhere check runs after the invite check, review L4). The DO row is kept until `exp + 300s` (`OIDC_JTI_RETAIN_PAST_EXP_SECONDS`, review F2): `verifyOIDC` still accepts a token at `now == exp`, and a row that expired AT `exp` was swept by the replay's own consume and re-inserted (`join.oidc-jti.expiry-boundary`). `/auth/oidc/login` gets the same treatment — see the 1b row "OIDC token replayed as a session". Residuals: (F5) the DO legs, `/join` and `/auth/oidc/login`, are atomic with each other through the shared `oidc:<issuer>#<jti>` key; KV `jti:<jti>`, eventually consistent, is the only guard between them and the KV-only routes `/cert/gha`, `/cert`, `/token` (subject token) and `/bootstrap/claim`. A token spent at `/cert/gha` and presented at `/join` in the same instant at two edges can win both — the same window `/cert/gha` and `/token` already have with each other — and a KV write that fails AFTER the DO committed leaves the token spendable at the KV-only routes until exp. (F3) The audience is the literal `notme.bot`, shared by every deployment (staging, BYO `npx notme auth init`), while the jti stores are per deployment, so single-use holds per deployment only: a token minted for another deployment, or spent there, is fresh here. The per-deployment audience is a contract change, tracked under notme-e3dede. And single-use does not stop an attacker who can mint a FRESH token for X — only a server-issued nonce bound into the proof does, which is notme-e3dede (GitHub Actions' `getIDToken` takes only an audience, so a nonce can be bound only through the audience, a change to the `notme.bot` contract pin). The `linkFederatedId` RPC no longer moves an existing link (plain `INSERT`, `federated.link.no-replace`, review I1). No client in this repo calls `/join` with an OIDC proof. | `join.oidc-jti.replay`, `join.oidc-jti.spent-elsewhere`, `join.oidc-jti.spends-shared`, `join.oidc-jti.independent-of-link`, `join.oidc-jti.refusal-keeps-token`, `join.oidc-jti.concurrent`, `join.oidc-jti.required`, `join.oidc-jti.expiry-boundary` |

### 9. credential vault — RETIRED, not a notme surface

This section used to carry 17 threat rows and 5 test-file names for a
credential vault under `vault/`. **notme has no vault.** It was deleted in
[ADR-012](../docs/design/012-vault-retirement.md) (`notme-9af5dd`) — cloister
owns and deploys the credential vault, and notme retains no copy. The
`vault/` path in this repo holds nothing but a stale `node_modules`.

The rows are gone rather than marked, because this document's contract is
that every identifier in a test column names a test that exists here. Every
one of those 17 named a file in `vault/src/__tests__/` that this repo does
not contain, so they asserted verified defences for a subsystem that is not
deployed from here and cannot be — the strongest form of the drift the
document exists to prevent (notme-8eed12).

For the live vault's threat model, see cloister. For why the split happened,
ADR-012; for the contract boundary that survived it,
`contract.vault.aad-binding` in `threat-model.test.ts`, which is an
`it.todo` reading "moved-to-cloister".

## out of scope (v1)

- CF infrastructure compromise (trust boundary — same as any cloud provider)
- WebAuthn authenticator compromise (hardware security — user's responsibility)
- DDoS (CF's WAF/DDoS protection handles this)
- browser vulnerabilities (user's responsibility)
